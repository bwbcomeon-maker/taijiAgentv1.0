# 太极 Agent 开发生命周期规范

本文是本项目唯一的完整开发生命周期规范。它覆盖任务进入、直接在 `main` 开发、本地验证、Sol 审核、提交与推送，以及另行授权的版本和交付动作。凡涉及仓库文件修改、Git/GitHub、源码启动、运行目录、持久服务、制包或发布，都必须先阅读并遵循本文。

Supporting runbook 只提供受本文约束的操作细节，不得改变授权边界、状态口径或门禁；若有冲突，以本文为准：

- 单人开发、提交、推送与恢复：[`solo-development-workflow.md`](./solo-development-workflow.md)
- Kylin/UOS 制包、离线安装与目标机证据：[`taiji-kylin-uos-offline-delivery.md`](./taiji-kylin-uos-offline-delivery.md)

当前明确任务边界及有效项目规则优先于旧记忆；旧记忆不能覆盖当前授权或作为现状证明。根 `AGENTS.md` 指定项目内 Skill，同名全局 Skill 不替代该版本。文档与脚本不一致时报告差异并保留实际门禁，不把未实现能力写成可用。本轮规则修订仍按修改前有效授权执行，不能通过待提交规则自行扩大权限。

## 1. 核心口径

### 1.1 `main` 与版本身份

- 日常开发直接在 `main` 进行。`main` 是日常开发主线，不等同于稳定版本。验证结论必须绑定具体提交或明确的工作树内容；分支名不构成验证证据，也不自动代表已制包、已安装或已发布。
- RC 使用不可移动的 `vX.Y.Z-rc.N` 附注标签（annotated tag）。稳定版本使用不可移动的 `vX.Y.Z` 附注标签。
- GitHub Release 只能绑定一个正式稳定标签。分支名、普通提交、CI 运行或轻量标签都不能替代该版本身份。
- 创建或推送 Tag、创建 GitHub Release、制包、签名、安装、部署、目标机验收及对外发布均不属于日常源码提交，必须逐项核对明确授权；已有版本标签不得移动。

### 1.2 交付状态不得混用

| 状态 | 最低证据 | 可以宣称 | 不可以宣称 |
| --- | --- | --- | --- |
| 本地改动已验证 | `main` 工作树中的目标 diff 已通过适用本地验证和 Sol 审核 | 当前改动已在本地验证 | 已提交、已推送、已发布 |
| 开发提交已推送 | 本地 `main` 精确提交已正常推送并与 `origin/main` 对齐 | 最新开发提交已进入远端 `main` | 稳定版本、制品已生成 |
| RC/稳定版本已标记 | 已授权的附注标签精确指向经发布预检的提交 | 对应 RC 或稳定版本身份已建立 | 已创建 Release、已安装 |
| 制品已生成 | 从绑定提交生成候选制品；版本、摘要与构建门禁闭合 | 当前制品已生成 | 安装态已验证、已发布 |
| 安装态已验证 | 绑定候选制品在明确环境完成适用安装、启动、升级/卸载验收 | 该制品在指定环境已验证 | 其它环境已通过、已发布 |
| 已发布 | 发布审批、版本/制品、渠道/环境、回滚入口全部闭合 | 已发布到明确渠道、环境和版本 | 未验证环境也已通过 |

“测试通过”、`Main Validation` 通过、窗口可见或目标机截图只能证明各自所在层。未实时核对的项目必须写“未验证”，旧记录只能写“历史线索”。

### 1.3 不可破坏的边界

- 禁止 force push、改写共享历史、`git reset --hard`、`git clean`、宽泛暂存、覆盖他人改动或删除归属不明的内容。
- 共享 `main` 出现错误时优先使用 `git revert` 产生可审计的反向提交；不得靠移动分支、移动 Tag 或覆写远端隐藏问题。
- 源码、运行时、配置、制品、安装态和发布渠道是不同对象；任一层的证据不得跨层推导。

## 2. 六个状态的日常开发流程

### 状态 1：绑定来源与单写入所有权

修改前必须记录并核对：

```bash
pwd -P
git rev-parse --show-toplevel
git rev-parse --git-common-dir
git branch --show-current
git rev-parse HEAD
git status --short
git worktree list --porcelain
```

- 实际仓库必须是预期根目录，当前分支必须是 `main`，HEAD 和远端基线必须可说明。
- 同一共享工作树及 Git index 同一时间只有一个协调后的写入者，覆盖跨任务场景。Sol、规范审查和质量审查可并行，但必须只读。
- 已有脏内容时逐路径判断归属；当前任务内容可继续收口，无关内容不得夹带、回退或清理。
- 发现错误仓库、detached HEAD、未知写入者、同路径并发写入或来源不一致时停止修改，先恢复唯一所有权。

### 状态 2：在 `main` 本地开发

- 在正式根目录的 `main` 直接开发；分支/worktree 是第 8 节的例外工具，不是日常前置步骤。
- 修改前理解架构、调用链、测试和运行方式；优先最小必要改动，禁止夹带无关重构、格式化、依赖升级或产品行为变化。
- Bug 优先复现、定位根因并说明影响面；证据不足时写“根因未确认”。同一故障假设最多两次诊断或修复，仍失败则停止该路径、回退试探性改动并保留证据，不猜测根因。能自动化时先建立会失败的回归测试，再修根因。
- 新能力先固定验收标准、入口、兼容边界和失败行为；用户可见前端还须执行项目 UX QA 门禁。
- 禁止提交凭据、私钥、客户数据、用户会话、真实配置、日志、缓存或临时制品。

### 状态 3：RED/GREEN 验证与 Sol 审核

- 行为变更先保留 RED 证据，再实现并证明 GREEN；文档或纯配置改动执行相应合同与静态检查。
- `scripts/verify.sh` 是统一日常入口：默认按当前 staged、unstaged、untracked 改动分级；高风险或不确定改动执行 `scripts/verify.sh --full`。
- 浏览器 smoke 是隔离的可选模式。缺少前置依赖或未执行时必须写“未验证”，不得把跳过写成通过。
- 精确暂存前可由 Sol 预审工作树；真正授权 commit 的最终审核必须在精确暂存后执行，不能由预审替代。
- `Main Validation` 是 push 后异步、非强制的补充证据；它不替代本地验证、Sol 审核、真实桌面或目标环境验收。
- 默认一次自审和一轮修正；达到修复轮次上限仍有阻断项时停止提交并报告，不无限循环。Sol 审核不可用或无法获得时停在提交前；不新增必须由 Luna/Spark 执行的要求。

### 状态 4：精确暂存与本地提交

- 只用明确路径暂存；不得用 `git add -A`、`git add .` 或相近宽泛命令夹带他人内容。
- 暂存后、commit 前，Sol 必须重新审核 `git status --short`、完整未暂存 `git diff`、`git diff --cached --name-status`、`git diff --cached --check` 和完整 `git diff --cached`，并把审核结论绑定到这组 staged bytes。
- 任何 staged bytes 变化（包括修复、重新暂存、增删路径或执行位变化）都会使旧审核失效；必须重跑受影响验证和上述全部最终审核视图。
- 提交信息使用 Conventional Commits，例如 `fix: ...`、`feat: ...`、`docs: ...`、`test: ...`、`refactor: ...`。
- 只有最终审核通过才能 commit。一个提交表达一个可审查目的；提交后记录 commit hash，并确认剩余工作树内容的归属。

### 状态 5：刷新远端、证明无远端领先并正常推送

- 本地提交完成后执行 `git fetch origin main`，证明 `origin/main` 是本地 `HEAD` 的祖先且远端领先数为零。
- 只有提交范围、适用验证、Sol 审核、远端分歧检查全部闭合，才允许正常 `git push origin main`。
- 禁止强推。远端存在领先提交、历史分叉、权限/网络错误或身份不明时立即停止推送，保留本地提交并按 supporting runbook 恢复；不得自动 rebase、reset 或覆盖远端。
- 推送后核对本地 `HEAD`、`origin/main` 和远端分支 SHA 一致；异步验证尚未结束时如实记录，不等待它来补发本地完成许可。

### 状态 6：另行授权的版本与交付门禁

- RC/稳定 Tag、GitHub Release、制包、签名、安装、部署、持久服务、目标机验收、升级、回滚演练和对外发布均需单独授权。
- **Tag 前候选检查**：普通候选先证明 clean main；已获授权的稳定版 hotfix 则证明 clean 非 `main` 临时分支/worktree 精确起于已发布稳定基线 Tag，且相对基线只含获批修复。两种来源都必须证明根目录与 Desktop 版本一致、Release Notes 为非空普通文件，并通过 `scripts/verify.sh --full`。该阶段不运行要求新 Tag 已存在的发布复验，也不创建 Tag。
- 只有取得具体 Tag 的明确授权后，才能为上述确定 commit 创建 annotated Tag；Tag 授权不自动授权 Release。
- **Tag 创建后**，普通 `main` 候选立即运行 `scripts/release-check.sh --tag <tag> --release-notes <绝对路径>`；已获授权的稳定版 hotfix 临时分支/worktree 则必须额外显式传入 `--hotfix-from <已发布稳定基线Tag>`。脚本证明附注标签精确指向 HEAD、版本与 notes 一致，并复验 `scripts/verify.sh --full`。Hotfix 模式还验证基线和候选均为附注稳定语义化版本、候选是同一主次版本的更高修订版、基线是 HEAD 祖先、当前为 clean 非 `main` 分支；它不联网证明基线已有 GitHub Release，该发布身份仍须独立核验。只有复验通过，才可分别申请和执行推送 Tag、创建 GitHub Release；脚本自身不创建、移动或推送标签，不创建 Release 或制品。
- Linux 候选还必须执行既有 `scripts/taiji-release-check.sh`，闭合 DEB、签名、认证矩阵和 GitHub CI 证据；该额外门禁不属于日常 `verify.sh`。

## 3. 用户授权语义

| 用户意图 | 已授权 | 必须明确的对象与边界 | 未授权 |
| --- | --- | --- | --- |
| 仅分析、审查或制定计划 | 只读检查和建议，不触发修改或 commit/push | 本次分析对象与证据范围 | 修改、提交、推送和交付动作 |
| 要求修改、修复或完成仓库任务，且未限定 `local-only` | 完成开发、本地验证、精确暂存、最终 Sol 审核、commit、刷新远端并正常 push `main`；无需再次询问 | 仓库、任务范围、验收标准、提交路径、目标 `origin/main`、回滚入口 | 强推、历史改写、Tag、Release及所有交付动作 |
| “按标准收尾” | 明确采用上一行的默认连续流程 | 当前任务、提交路径、目标 `origin/main`、回滚入口 | 强推、历史改写、Tag、Release及所有交付动作 |
| “仅本地”“`local-only`” | 本地开发、验证和审核；停在用户指定的本地边界 | 仓库、任务范围、停止点 | push、Tag、Release及所有交付动作 |
| “本地预览”“给我看看效果” | 从当前源码以 development 模式启动隔离预览 | 源码根、解释器/入口、runtime/config、端口 | 持久服务、真实用户状态变更、安装、发布 |
| “创建 `<版本>` Tag” | 为已完成 Tag 前候选检查的明确 commit 创建指定附注标签 | commit、标签名、版本、是否 RC/稳定、不可移动约束 | GitHub Release、推送 Tag、制包、安装、发布 |
| “创建 GitHub Release” | 为已通过 Tag 后 `scripts/release-check.sh` 复验的指定稳定标签创建 Release | 稳定标签、Release Notes、目标仓库、发布状态 | 制包、安装、部署及其它渠道 |
| “为 `<commit/版本>` 制包” | 从已复验来源生成指定平台候选制品 | commit/Tag、版本、平台、输出、旧制品与回滚边界 | 安装、分发、发布 |
| “在 `<目标机>` 安装/验收 `<制品>`” | 在指定主机对绑定摘要的制品执行约定动作 | 制品摘要、主机/系统、数据影响、回滚路径 | 其它主机、扩大清理、发布 |
| “发布 `<版本>` 到 `<渠道/环境>`” | 将绑定版本/制品发布到指定渠道或环境 | 版本、摘要、渠道、受众、停止与回滚条件 | 其它版本、渠道或扩大投放 |

- 对普通修改/修复/完成任务，用户未限定 `local-only` 时，默认流程在所有本地门禁通过后连续完成精确 commit、远端刷新和正常 push `main`，不重复请示。“按标准收尾”只是该流程的明确快捷语义。
- 用户明确要求“提交”“保存一下”或 `local-only` 并给出本地停止边界时，按该更具体边界停止，不擅自扩大为 push。
- 任一授权只覆盖当前明确成果，不延伸到无关 ref、历史改写、其它主机、安装态或发布渠道。
- 同一对象、阶段、主机及影响范围内仍有效的授权可以跨轮延续，不因用户说“继续”而清零；对象、commit/制品摘要或影响范围变化时重新核对授权。新增阶段仅暂停未授权部分，已授权且不依赖该部分的工作可以继续。既有脚本的明确确认机制仍须执行。
- 外部动作执行前必须闭合：对象、commit/版本/制品摘要、主机/环境/渠道、破坏性范围、备份与回滚。缺一项即暂停。

## 4. 单写入、长任务与依赖关系

- 协调者必须明确唯一写入 Agent 的文件所有权；其他 Agent 只能审查或调查，不得编辑、暂存或提交。
- 并行只读审查不得改变运行进程、依赖目录、Git index、远端或用户状态。
- 长任务用小而稳定的本地提交和状态卡保存可恢复边界；checkpoint 不能冒充完成。
- 接口、流程、支持范围或门禁变化时更新手册；当轮执行结果写入验证台账。历史日志和一次性操作不堆入根 `AGENTS.md`。
- 后续任务依赖前置任务时，优先让前置提交进入 `main` 后再开始。必须并行时记录基线、依赖 commit、热点文件所有权和复验范围。
- 冲突必须理解双方意图后最小解决；禁止用覆盖整个文件、丢弃对方变更或改写历史代替冲突分析。

## 5. 运行来源与预览门禁

- 启动和测试必须显式固定源码根、Agent/WebUI/Electron 入口、Python/Node 解释器、runtime-home、用户配置快照和端口。
- 前后端跨目录加载时核对 `HERMES_WEBUI_AGENT_DIR`、解释器、`PYTHONPATH` 和关键模块 `__file__`；从错误目录加载的结果作废。
- 运行态证据至少包括：进程命令、物理 cwd、监听端口、源码 commit、工作树状态、静态资源身份和配置来源。
- 自动化与常规调试使用 mock、fixture 和隔离配置/资料目录，不打开默认浏览器或真实 OAuth/Provider 页面。真实 OAuth、Provider、日常用户状态或外部打开动作按明确授权范围执行。
- development 预览只能证明当前源码与当前 runtime/config；不能替代安装态、发布态或目标机证据。
- 最终报告应分别给出源码 commit、实际入口、进程/模块来源、runtime/config 边界和验证结果；未核对项写“未验证”。

## 6. 验证与证据分工

| 门禁 | 目的 | 不能替代 |
| --- | --- | --- |
| 本地 `verify.sh` | 提交前证明当前 diff 与受影响回归 | 真实桌面、目标机、安装态 |
| Sol 审核 | 核对目标、范围、证据和风险 | 自动化测试、用户验收 |
| 异步 `Main Validation` | push 后在独立环境补充验证和发布证据 | 本地门禁、真实 Provider、目标机 |
| 人工/真实 Electron | 验证入口、交互、窗口与配置边界 | 安装态、Kylin/UOS 目标机 |
| 安装态/发布态 | 验证制品、路径、升级/卸载和分发 | 未测试平台或客户环境 |

- 文档改动可走快速本地范围；普通代码运行根合同与受影响模块；工作流、依赖、认证、凭据、Provider、授权、迁移、打包、发布改动升级为全量本地验证。
- 风险不确定时只能升级验证范围。自动化、人工、安装态和目标环境证据相互补充，不能互相替代。
- 未执行的浏览器、截图、可访问性、视觉回归、真实 Provider 或目标环境检查必须标记为“未验证”。
- 异步运行失败必须调查其真实原因，但它不是日常 push 的 required check；正式发布链若引用该运行，则必须按发布门禁取得成功且身份匹配的证据。

## 7. 提交后的恢复与回滚

- push 前发现错误：继续在本地修复、重跑验证和审核，再建立清晰提交；不得靠丢弃工作树掩盖问题。
- push 后发现错误：优先 `git revert <bad-commit>`，对 revert 改动执行同样的本地验证、Sol 审核、精确暂存和正常推送。
- 远端领先或分叉：停止推送并保留本地提交；按 runbook 创建明确备份后，在受控例外分支/worktree 中基于最新远端重新集成，不得覆盖远端。
- 网络、权限或 GitHub 不可用：保留本地提交和证据，待外部状态恢复后重新 fetch、检查分歧并正常 push。
- 任何回滚必须说明受影响版本、数据/迁移兼容性、验证范围和后续修复条件。

## 8. 分支/worktree 的批准例外

任何分支/worktree 例外开始前都必须先取得用户对具体例外的明确授权，并明确基线、目的、写入者、整合和清理边界。以下列举只是可以申请例外的特殊场景；列举或符合这些场景不构成授权，也不能由 Agent 自行批准：

- 已发布版本的紧急 hotfix；
- 高风险重写、框架/依赖大升级或长时间破坏性实验；
- 多个 Agent 确需并行写源码；
- 同时维护多个已发布版本；
- 远端领先后需要保护本地提交并重新集成。

例外必须记录基线、分支、worktree、写入者、依赖、集成顺序、验证范围、回滚与清理条件。进入 `main` 前仍须完成适用本地验证、Sol 审核和明确整合；不得把例外变回所有日常改动的固定成本。

已发布版本 hotfix 的基线必须是目标版本的已发布稳定 Tag；不得以 `origin/main` 或其它开发线作为 hotfix 起点，也不得把 `main` 中尚未发布的功能或改动混入修订版。严格按以下顺序执行：

1. 从已发布稳定 Tag 创建临时 branch/worktree，并绑定目标版本、Tag、commit 和唯一写入者。
2. 只实施单一 hotfix，不夹带重构、依赖升级或其它开发线内容。
3. 完成完整验证和 Sol 审核，证明修订候选只包含该修复且仍满足发布门禁。
4. 另行授权创建修订版 annotated Tag；该 Tag 使用同一主次版本下更高的新修订版本号，不能移动或复用原 Tag。
5. 在 clean 临时分支/worktree 中执行 `scripts/release-check.sh --tag <新修订Tag> --release-notes <绝对路径> --hotfix-from <已发布稳定基线Tag>`；未显式声明基线的 linked worktree 必须拒绝。该检查不替代对基线 GitHub Release 身份的独立核验。
6. 复验通过后，另行授权推送 Tag；再另行授权创建对应 GitHub Release。创建 Tag、推送 Tag 和创建 Release 是三个独立边界。
7. 将相同修复同步回 `main`，按日常流程重新验证、审核、提交并正常推送，防止后续版本回归。
8. 审计后删除临时 branch/worktree；必须先证明修复已进入修订版本和 `main`，且没有未吸收提交、未跟踪内容、关联进程或待保留证据。

清理分支/worktree 前审计所有 refs、工作树状态、未跟踪内容、仅分支提交、关联进程和备份。价值不明或未吸收的内容不得删除；未闭合审计时禁止强删或执行 `git gc --prune`。

## 9. 导入、持久服务与高影响边界

### 9.1 Monorepo 导入

- 接受显式仓库路径的工具必须清除 Git 定位环境变量，并用对抗性测试证明不会串库。
- 独立仓库导入后，必须用 `scripts/check-imported-source-tree.py` 逐路径证明源 commit 已被父仓库跟踪；刚导入时加 `--require-content-match` 核对 blob 与执行位。
- 精确强制加入被误 ignore 的有效路径，不能整体放宽 ignore；提交后从 archive 或全新 clone 做关键复验。

### 9.2 持久服务

macOS `LaunchAgent`、后台守护进程和登录自启动属于部署边界，不是 development 预览。

- 可执行文件、工作目录、日志和 runtime-home 必须使用产品安装目录或用户数据目录，不得依赖开发仓库/worktree。
- 安装、启停、卸载前核对 label、版本、路径、日志/数据影响与回滚；这些动作均需明确授权。
- 用户配置、会话和日志不是代码垃圾，不得随开发清理删除。

## 10. 发布交接

当前 Linux 输入链仅接受已复验的 clean `main`，Linux hotfix 分支制包尚未支持。第 8 节及通用 `release-check.sh --hotfix-from` 支持源码修订和发布身份检查，不代表 Linux `99/00/01` 链支持该来源；不得绕过来源门禁生成 hotfix DEB。下述 hotfix 制品规则只适用于实际支持该来源的平台链。

- 普通候选制品只能来自已通过发布预检、身份明确的 `main` 提交和相应 Tag；已获授权的 hotfix 候选只能来自第 8 节绑定的已发布稳定基线及其受控修订 Tag。工作树改动、旧制品或未绑定提交不得作为来源。
- GitHub Release 的 name 必须与稳定 Tag 完全一致；正文必须包含 Release Notes 以及安装或升级说明。
- Release 资产必须来自该 Tag 对应的 commit，并逐项记录 basename、字节数和 SHA256，确保源码、制品和 Release 身份闭合。
- 已发布资产不得静默覆盖、替换或用同名内容改变摘要；发现问题时必须发布新的修订版本，并重新执行 Tag、Release、制品和验证门禁。
- 发布交接至少记录：源码 commit、Tag、正式根目录状态、启动/制包入口、runtime/config、验证结果、制品 basename/字节数/SHA256、目标环境、已知风险和回滚入口。
- Linux/Kylin/UOS 还须遵循 [`taiji-kylin-uos-offline-delivery.md`](./taiji-kylin-uos-offline-delivery.md) 与项目指定 skill；没有绑定当前制品的目标机证据，不得宣称已完成离线交付或目标机验收。
- 正式报告明确区分“已实时验证”“未验证”“历史线索”。

## 11. 每轮状态卡

状态卡用于实施、运行和交付任务；仅分析、审查或制定计划无需输出开发收尾状态卡。

```markdown
### 任务状态卡

- 任务：<一个独立成果>
- 仓库/分支/HEAD：<绝对根目录；main 或批准的例外分支；commit>
- 写入所有者：<唯一写入 Agent；只读审查者>
- 阶段：<来源绑定 / main 本地开发 / 验证与审核 / 已提交 / 已推送 / 版本或交付门禁>
- 交付口径：<本地改动已验证 / 开发提交已推送 / 版本已标记 / 制品已生成 / 安装态已验证 / 已发布>
- 已完成：<有当前证据的事项>
- 未完成：<待实现、待授权、待验收或未验证事项>
- 验证：<命令、实际结果、环境边界>
- 来源：<源码、进程/模块、runtime/config、制品身份>
- 下一触发条件：<修复 / 正常推送 / Tag 授权 / 制包授权 / 目标机验收等>
```

状态卡必须与事实一致：未提交改动只处于本地开发；本地验证不等于已推送；开发提交推送不等于稳定版本；附注标签不等于 Release；制品生成不等于安装态或发布态。
