## 1. 项目定位

甲方拟采购的不是针对某个特定场景开发的单一 AI 应用，而是一套能够由甲方自主使用并持续建设 AI 能力的企业级工业 AI 平台。

平台应以中心侧 AI 引擎为核心，以场站边缘算法调度组件为延伸，统一管理数据、知识、模型、算力、算法、智能体和应用，形成从现场数据采集、模型训练到边缘部署、告警应用和数据回流的完整闭环。

产品形态可概括为：

> AI 用户服务中心＋中心侧 AI PaaS＋场站边缘节点＋云边协同算法调度体系。

## 2. 建设目标

甲方希望获得一套可持续生产 AI 能力的工具平台，使内部人员及第三方厂商能够在平台上自主完成：

- 数据接入和加工；
- 数据集构建与标注；
- 传统小模型及 CV 模型训练；
- 大模型训练、微调和评估；
- 模型注册、管理、部署和推理；
- GPU 及异构算力资源调度；
- CV 算法编排和调度；
- Agent、Skill 和 MCP 开发；
- 知识库和 RAG 应用构建；
- AI 应用发布和运维；
- 场站数据回流及模型持续迭代。

平台需要解决第三方 AI 产品难以适配甲方项目、重复建设、数据和算力分散、模型及算法无法统一管理等问题。

## 3. 总体架构

### 3.1 AI 用户服务中心

AI 用户服务中心是平台面向业务人员、算法工程师、Agent 开发人员、第三方厂商和平台管理员的统一入口，预期包括：

- AI 能力服务目录；
- AI 应用访问入口；
- Agent 应用目录；
- 开发者工作台；
- 算法和模型服务申请；
- 应用发布与管理；
- 使用情况和运行状态查询；
- 平台运营管理。

### 3.2 中心侧 AI 引擎

中心侧 AI 引擎部署在甲方中心机房或私有云环境，统一承担：

- 多元数据接入和治理；
- 知识加工及检索推理；
- 模型训练、微调、评估和管理；
- 模型推理服务；
- GPU 及异构算力调度；
- 算法仓库及算法调度；
- Agent、Skill、MCP 和应用构建；
- 边缘节点及边缘算法统一管理；
- 运行监控、权限控制和审计。

### 3.3 场站边缘侧

光伏场站等现场存在摄像头和物联网设备。原则上每个场站部署一套边缘算法调度组件或边缘服务器，负责：

- 对接摄像头和物联网设备；
- 视频拉流、编解码和预处理；
- CV 模型本地推理；
- 算法任务运行和资源分配；
- 识别结果及报警输出；
- 弱网、断网环境下持续运行；
- 接收中心下发的模型、算法和配置；
- 将告警、运行数据及有效样本回传中心。

### 3.4 云边协同

中心侧需要统一管理各场站，实现：

- 边缘节点注册和纳管；
- 算法、模型及配置下发；
- 算法启停和任务调度；
- 模型及算法版本升级；
- 灰度发布和失败回滚；
- 中心与场站之间的资源协同；
- 边缘节点运行监控；
- 告警和推理结果回传；
- 现场样本及数据回流；
- 多场站统一运营和运维。

## 4. 中心侧三大能力方向

- 物联网监测数据；
- 摄像头视频流；

- 设备运行及报警数据；

- 图片、视频及文本标注；
- 数据集构建；
- 数据集版本管理；
- 数据质量管理；
- 数据分类分级；
- 样本回流和训练数据更新。

### 4.3 智能体构建与运营

## 5. 模型全生命周期

平台需要同时管理传统 CV 小模型和大语言模型。

### 5.1 模型开发与训练

- 小模型训练；
- 摄像头图像识别模型训练；
- 视频分析算法训练；
- 大模型全参数微调；
- LoRA 等参数高效微调；
- 自定义训练代码和镜像；
- 单机及分布式训练；
- 训练任务监控；
- 断点续训。

### 5.2 模型评估

- 训练过程指标；
- 模型版本对比；
- 测试集评估；
- CV 准确率、召回率、误报率和漏报率；
- 大模型效果评测；
- 人工评测；
- 模型上线门禁；
- 评估报告。

### 5.3 模型管理

- 模型统一注册；
- 模型仓库；
- 模型版本管理；
- 模型适用场景管理；
- 模型审批；
- 模型制品和依赖管理；
- 模型发布、下线和回滚。

### 5.4 模型推理

- 中心侧在线推理；
- 批量推理；
- 场站边缘推理；
- 推理 API；
- 推理限流和配额；
- 弹性扩缩容；
- 推理监控；
- 支持主流开源模型、国产模型和商业模型。

商业模型需要进一步区分是通过外部 API 接入，还是要求私有化部署。

## 6. 算力资源管理

甲方已有数台 GPU 服务器及相应调度软件。新平台原则上应优先考虑纳管、复用或对接现有资源，而不是未经评估直接替换。

需要具备：

- GPU 服务器纳管；
- 训练和推理资源池；
- 用户、部门和项目配额；
- 任务队列；
- 优先级调度；
- 抢占式调度；
- GPU 切分或共享；
- 训练与推理混合调度；
- 算力使用率监控；
- 卡时和使用量统计；
- 故障监控和告警；
- 国产 GPU、NPU 等异构算力适配。

需要特别区分：

- **GPU 资源调度**：调度计算资源；
- **CV 算法调度**：调度场站算法、摄像头和推理任务。

两者属于不同的产品能力，不应在需求、方案和验收中混为一体。

## 7. 算法调度管理

算法调度组件是甲方一期最优先建设的能力。

主要需求包括：

- 算法注册；
- 算法包和版本管理；
- 多厂家算法接入；
- 算法与摄像头绑定；
- 一个算法处理多个视频流；
- 一个视频流运行多个算法；
- 算法参数和阈值配置；
- 算法运行时段配置；
- 算法任务优先级；
- 中心和边缘资源选择；
- 算法远程下发；
- 算法启停；
- 算法升级及回滚；
- 运行状态和性能监控；
- 算法效果统计；
- 告警规则；
- 正误报反馈；
- 困难样本回流；
- 算法持续训练及优化。

其中部分细项是依据甲方目标推导出的必要能力，仍需甲方逐项确认。

## 8. 视频和物联网集成

平台需要对接甲方现有物联网和视频体系，包括：

- 物联网平台；
- 场站设备；
- 摄像头；
- 视频管理平台；
- 视频流；
- 视频编解码；
- 视频解析；
- 视频分析；
- 视频报警；
- 事件中心；
- 业务处置系统。

需要进一步明确：

- 摄像头品牌、型号和数量；
- RTSP、GB28181、ONVIF 等协议；
- H.264、H.265 等编码格式；
- 视频分辨率和并发路数；
- 是否允许直接连接摄像头；
- 是否必须通过现有视频平台；
- 报警信息的接收和处置系统；
- 视频、截图及事件片段的保存规则。

## 9. 数据回流闭环

甲方明确要求“从数据到数据”形成完整闭环：

```text
现场视频和监控数据
→ 数据采集
→ 数据筛选和治理
→ 样本标注
→ 训练数据集
→ 模型训练或微调
→ 模型评估
→ 模型注册
→ 中心或边缘部署
→ 算法推理
→ 识别结果和报警
→ 人工确认
→ 正误报及困难样本回流
→ 重新训练
→ 新模型评估
→ 灰度发布
→ 持续迭代
```

该闭环是项目核心验收对象，不能只验证模型训练或边缘推理中的单个环节。

## 12. 一期建设重点

### 12.1 客户明确的优先方向

客户明确提出第一步优先建设算法调度组件，并要求场站侧具备相应能力，形成云边协同。

该表述目前只能确认一期的**优先方向**，尚不能直接推导出完整的一期合同范围、设备数量和验收指标。

### 12.2 建议的一期 MVP

基于客户优先方向，当前建议的一期 MVP 主线是：

> 先建设算法调度管理组件，选择试点场站部署边缘节点，打通中心与场站之间的云边协同和 CV 算法数据闭环。

建议 MVP 包括：

1. 建设中心侧算法调度管理组件；
2. 选择一个或少量试点场站；
3. 按经确认的部署模式配置试点边缘节点；
4. 对接现有摄像头和视频平台；
5. 完成视频拉流、编解码和分析；
6. 接入至少一个 CV 算法；
7. 完成算法与摄像头绑定；
8. 完成模型和算法远程下发；
9. 完成边缘本地推理；
10. 完成报警及识别结果回传；
11. 验证最小可行的正误报反馈和样本回流；
12. 为后续训练、评估、版本升级及回滚预留接口。

### 12.3 建议在一期范围确认后再决定的能力

以下能力与总体目标相关，但是否纳入一期尚未得到甲方明确确认：

- 完整的重新训练和自动化评估流水线；
- 模型及算法灰度升级和自动回滚；
- 甲方现有 GPU 资源的全面纳管或调度软件替换；
- Agent、MCP、知识库及 AI 用户服务中心的完整建设；
- 多场站批量推广；
- 高可用、灾备和完整运营体系。

## 14. Taiji Agent 与本项目的关系

当前 Taiji Agent 属于平台上层的智能体应用和运行工作台。各层责任边界暂按下表理解：

| 能力范围 | 当前 Taiji Agent | 需新建或集成的平台能力 | 最终责任方 |
| --- | --- | --- | --- |
| Agent 交互、多智能体、Skill、MCP 调用 | 可作为现有能力基础 | 需要接入统一模型、知识、权限和运营体系 | 待方案及采购拆包确认 |
| AI 用户工作台、上层示范应用 | 可作为原型或入口候选 | 需要补齐统一门户、应用目录和平台运营 | 待确认 |
| 数据治理、标注和数据集 | 不具备完整平台能力 | 需要数据平台或 AI 开发平台 | 待确认 |
| 模型训练、评估、部署和推理 | 不具备完整平台能力 | 需要 MLOps/训推平台 | 待确认 |
| GPU 及异构算力调度 | 不具备 | 需要算力调度平台或对接现有软件 | 待确认 |
| 视频接入、CV 算法调度和报警 | 不具备 | 需要视频及算法调度平台 | 待确认 |
| 边缘节点和云边协同 | 不具备 | 需要边缘管理平台及场站组件 | 待确认 |
| 信通院能力测评 | 未验证且不能继承 | 由实际投标和交付产品提供对应证据 | 待甲方明确测评口径 |

Taiji Agent 可以复用的方向包括：

- Agent 交互；
- 多智能体协作；
- Skill 和 MCP 调用；
- 文档和知识类任务；
- AI 用户工作台；
- 上层示范应用。

当前 Taiji Agent 不能独立满足：

- 数据标注和 CV 训练；
- 大模型完整训推平台；
- GPU 集群调度；
- 视频接入和编解码；
- CV 算法调度；
- 场站边缘节点管理；
- 云边协同；
- 视频报警；
- 数据回流闭环；
- 完整工业 AI PaaS；
- 信通院平台能力测评要求。

因此，Taiji Agent 更适合作为整体平台中的智能体工作台、Agent 运行入口或示范应用，而不是直接作为甲方采购的完整 AI 底座。

## 15. 已确认、分析归并与待确认边界

### 15.1 已从客户沟通中明确的需求

- 采购对象是 AI 平台能力，不是特定场景应用；
- 甲方需要自主构建 Agent 和 Skill；
- 需要小模型和摄像头图像识别训练；
- 需要对现有 GPU 服务器进行算力资源调度；
- 需要中心侧 AI 引擎；
- 需要数据处理、模型微调、评估、管理和推理；
- 需要算法调度、应用部署和数据回流；
- 每个场站需要边缘侧组件并实现云边协同；

## 17. 当前结论

本项目的核心不是开发一个 AI 应用，而是建设一条可以重复生产、部署和运营 AI 能力的工业化流水线。

短期抓手是场站 CV 算法调度、云边协同和数据回流；长期目标是形成覆盖数据、知识、模型、算力、算法、Agent 和应用运营的完整 AI 用户服务中心与中心侧 AI PaaS。
