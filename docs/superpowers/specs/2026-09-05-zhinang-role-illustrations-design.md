# 太极智囊角色配图设计

## 目标

为智囊目录中的每个角色提供一张能够体现角色定位的独立配图。视觉采用用户选定的轻量 3D 图标风格：柔和人物模型、磨砂玻璃信息板、蓝青品牌色和浅冰蓝背景。配图服务于角色识别，不承载文字信息，也不改变角色能力、提示词或任务创建流程。

## 视觉系统

- 每张图使用一个职业人物或明确的职业主体，并配置 2–3 个与角色能力直接相关的道具或符号。
- 统一为方形构图，主体位于中央安全区；缩小到卡片尺寸后仍能通过轮廓和核心道具区分角色。
- 固定蓝、青、深海军蓝、白和冷灰色系；材质为柔和哑光聚合物与克制的磨砂玻璃。
- 保持明亮、可信、专业和亲和，避免儿童玩具感、通用机器人、复杂会议场景与过量装饰。
- 禁止生成文字、字母、数字、Logo、水印、边框和品牌商标。
- 人物在年龄、性别、发型和服装上适度变化；变化必须服从职业识别，不使用真实人物身份。

## 角色到画面的映射

生成输入以固定中文角色目录为唯一来源。每个角色从以下字段提取画面语义：中文名称、原始名称、分类、摘要、能力、限制和标签。生成记录保存角色 ID、输入字段摘要、最终提示词、文件名、尺寸和 SHA-256，便于审计和重新生成。

每张图按以下顺序确定内容：

1. 从角色名称和摘要确定职业主体。
2. 从能力列表选择两个最具区分度的工作对象或动作。
3. 从分类选择一个统一的辅助视觉母题，但不以颜色作为唯一分类线索。
4. 删除无法在小尺寸辨认的细节，确保不同角色不会只靠换文字区分。

若角色描述不足以形成可靠画面，使用其分类的职业工作台作为回退，并在生成清单中标记为需要人工复核，不猜测敏感身份或未声明能力。

## 分批生成与验收

生成分两个阶段进行：

1. 先生成并接入以下固定 12 个代表角色：`agency:sales/sales-engineer`、`agency:sales/sales-proposal-strategist`、`agency:product/product-manager`、`agency:engineering/engineering-software-architect`、`agency:marketing/marketing-content-creator`、`agency:marketing/marketing-aeo-foundations`、`taiji:document-reviewer`、`agency:specialized/grant-writer`、`agency:specialized/accounts-payable-agent`、`agency:specialized/automation-governance-architect`、`agency:specialized/specialized-cultural-intelligence-strategist`、`agency:design/design-brand-guardian`。该集合覆盖六个分类以及人物型、流程型、技术型和文档型画面。
2. 12 张代表图完成代码与浏览器验收后停下，由用户查看卡片和详情实际效果。只有用户明确通过代表集，才允许生成其余角色；未通过则仅返工代表集，候选图不进入 `active` 状态。
3. 用户通过后生成其余角色。24 张只是数量上限；每批开始和收尾都以 `scripts/check-local-change-safety.py` 对完整当前变更集的实际统计为准，统计包含 staged、unstaged、untracked 的完整文件字节以及代码、完整清单、生成记录和其他已有改动。同一路径同时存在 staged 与 unstaged 内容时按门禁实际重复计量，必须动态减少本批图片数量，只有脚本 PASS 才能进入审核和提交。
4. 全部角色生成后对 274 张逐张完成视觉审核，清单必须证明 274 个当前可用角色均有唯一 `active` 映射，不能用代表集通过替代全量检查。

每个图片项按 `draft → review → approved → active` 流转。生成后为 `draft`，人工视觉检查后进入 `review`，用户明确批准后进入 `approved`，通过清单与文件校验并接入正式产品后才进入 `active`。正常运行的 API 只返回 `active` 项；其他状态一律使用单字回退。

代表集通过一个仅限隔离本地验收服务的预览通道展示：服务端必须同时满足显式环境变量 `TAIJI_ZHINANG_IMAGE_REVIEW=1`、请求来自 loopback、使用独立测试状态目录，才可在 API 响应中投影 `review` 或 `approved` 图片。该通道不读取客户端参数来开启，不写入用户正式状态，不在安装态或正式运行配置中启用。这样用户可以在真实卡片和详情中验收代表图，而未批准图片仍不会进入正常产品的 `active` 映射。

Image 2.0 生成原始 1024×1024 PNG。进入产品的文件统一转换为 512×512 WebP，保留源图比例，不裁掉主体，目标单图不超过 160 KiB。产品仓库只提交经过选择和压缩的 WebP、映射清单及必要生成记录；预览废稿不进入仓库。

## 文件与数据结构

- 产品图片目录：`hermes-local-lab/sources/hermes-webui/static/assets/zhinang/roles/`
- 文件名：将角色 ID 中除 ASCII 小写字母、数字和连字符外的字符统一替换为单个连字符，去掉首尾连字符，再追加角色 ID 的 SHA-256 前 8 位，例如 `agency-sales-sales-engineer-a1b2c3d4.webp`；规范化结果和最终文件名在清单内必须唯一。
- 映射清单：`hermes-local-lab/sources/hermes-webui/static/assets/zhinang/role-images.json`
- 清单顶层包含 `schema_version`、绑定的 `catalog_version`、生成批次和图片项。图片项包含 `role_id`、相对图片路径、SHA-256、宽高、文件字节数、实际生成模型标识、源 PNG SHA-256、WebP 转换参数、审核状态、审核人和审核时间。
- 加载时校验清单 schema 与当前 catalog 版本、角色 ID 唯一性、路径唯一性、状态只属于 `draft/review/approved/active`、SHA-256 为 64 位小写十六进制、尺寸固定 512×512、字节数不超过 160 KiB。
- 图片路径必须位于固定 `static/assets/zhinang/roles/` 前缀且以 `.webp` 结尾；拒绝协议、绝对路径、反斜杠、`..`、查询串和片段。目标必须是该目录内非符号链接的普通文件，解码结果必须为 WebP 512×512，实际字节数和 SHA-256 必须与清单一致。
- API 列表与详情响应增加受信任的站内相对图片路径；服务端只从通过上述校验的固定清单查找，不接受客户端传入或远程 URL。JSON 无法解析、顶层 schema 或 catalog 版本错误、重复角色 ID、重复路径属于整份清单失效并忽略全部映射；单个文件缺失、符号链接、解码失败、格式/尺寸/字节/SHA-256 不符只禁用该项。两种情况都必须退回单字标记，不能拖垮目录、详情、收藏或任务创建。

## 界面接入

- 卡片顶部用配图替换现有单字角色标记。图片使用固定比例容器和 `object-fit: cover`，加载期间保持卡片高度稳定。
- 详情页在标题下方显示同一张较大配图，不新增轮播、下载或图片操作。
- 配图与旁边角色名称和摘要语义重复，因此使用空 `alt` 并设为装饰内容，避免屏幕阅读器重复播报。
- 图片容器先显示现有单字标记；图片成功解码后原位替换。首次或重复加载失败都保留单字标记且不反复闪烁，不显示破图图标，也不能阻止查看详情、收藏或创建任务。不可用角色沿用现有禁用视觉并使用相同回退规则。
- 图片映射独立于收藏记录和 v2 会话快照，不向这两类持久数据增加图片字段。当前目录、下架收藏和历史详情均按 `role_id` 查询当前版本的 `active` 展示映射；映射更新或移除后随当前清单变化，缺失时使用单字回退，不把配图描述为不可变历史事实。
- 窄屏、200% 缩放和详情抽屉保持当前滚动、焦点与主操作位置。

## 验证标准

- 固定目录中的每个可用角色都有且只有一个有效图片映射，文件存在、尺寸正确、SHA-256 匹配。
- 12 张代表集在卡片缩略尺寸与详情尺寸下均能体现对应角色定位，无文字、Logo、水印或明显生成缺陷。
- 图片失败回退、目录加载失败、空状态、下架角色和历史详情不影响原有功能。
- 卡片、详情、收藏、筛选、分页、最近使用、键盘焦点和 Escape 关闭路径通过聚焦测试与真实浏览器验收。
- 桌面常用视口、窄屏和 200% 缩放下无布局跳动、溢出或主操作遮挡。
- 验证首屏只请求可见卡片图片，翻页与详情按需加载；记录图片请求数量、解码失败回退和加载前后布局尺寸。最终资源总量、每批新增字节、单图大小及应用构建体积增量在验证台账中记录；安装包与目标机验收仍属于单独交付阶段。

## 非目标与边界

- 本设计不改变角色提示词、能力、许可、来源数据或目录数量。
- 不为配图增加上传、编辑、下载、联网获取或用户自定义入口。
- 不使用远程图片地址，也不在运行时调用 Image 2.0。
- 本设计只授权源码资源生成和界面接入；Windows/Linux 制包、安装、签名、发布与目标机验收需要各自授权。
