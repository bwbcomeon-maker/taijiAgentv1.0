# 主模型 Provider 切换一致性设计

## 背景与根因

主模型运行路由由 `Provider + 模型 ID + Base URL + 凭据引用 + api_mode` 共同决定。当前页面只切换了 Provider，下游字段仍可能保留上一个 Provider 的值。已实际出现 Z.AI / `glm-5` 携带 DeepSeek Base URL，导致请求被发往错误服务并被误报为 API Key 无效。

## 本轮范围

只处理设置页“主模型配置”的 API Key 主链路：Provider 切换、模型选择、端点、尚未保存的密钥草稿、持久化通信模式及保存后的连接验证。不改图片能力、OAuth 流程、打包、发布或低概率兼容场景。

## 已批准行为

1. 用户切换 Provider 时，页面把模型自动切换为该 Provider 模型列表中的第一个推荐项；列表为空时清空模型，允许用户手工填写。
2. 同一次切换清空旧 Base URL 和尚未保存的 API Key 草稿，避免跨 Provider 串用。
3. 后端在 Provider 变化时清除持久化的旧 `api_mode`，并丢弃随请求原样回传的旧 Base URL。
4. 后端只拒绝“Provider 已变化、模型仍等于原配置、且静态目录明确判定该模型属于原 Provider”的明确旧模型串用。未知的新模型继续允许保存，避免内置目录滞后阻塞新模型。
5. 保存成功、连接验证、真实对话验证继续分层展示；连接检查不替代真实对话，也不额外触发计费调用。

## 失败行为

- 明确的旧模型串用返回可操作错误，提示重新选择新 Provider 的模型。
- 保存网络结果不确定时继续读取脱敏权威状态，不自动重放写请求，不回显或持久化浏览器中的密钥草稿。

## 验收标准

- DeepSeek 切换到 Z.AI 后，页面模型变为 Z.AI 推荐模型，旧端点与密钥草稿为空。
- 后端保存 Z.AI / GLM 时不保留 DeepSeek Base URL 或旧 `api_mode`。
- 后端拒绝明确的 DeepSeek 旧模型随 Provider 切换到 Z.AI。
- Z.AI 下手工填写未知的新 GLM 模型仍可保存。
- 原有同 Provider 保存、显式新 Base URL兼容行为、分层验证及不确定结果协调逻辑不回归。
