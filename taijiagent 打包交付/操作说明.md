# 太极 Agent 麒麟终端打包交付操作说明

## 文档分工与四级证据口径

研发和发布负责人应同时阅读源码仓库内的 `docs/runbooks/taiji-kylin-uos-offline-delivery.md`。该内部手册沉淀 Docker 演练边界、真实故障、诊断流程、registry lock 风险和目标机最终验收。本文描述的完整目录仅供内部制包、断网演练和真机验收；销售放行后客户目录只包含一个由统一兼容策略约束的 `.deb`。

打包和部署状态统一使用以下四级标签：

- **源码包已准备**：当前候选的唯一源码包、由该归档导出的不可变成员清单、basename/内容校验和源码发布预检通过。
- **制包机已构建**：兼容 Linux amd64 制包机生成单一 DEB、sidecar、manifest、构建报告和 `.build-success`，最终发布预检通过。
- **离线安装已演练**：当前交付目录在断网的干净 Linux amd64 容器、VM 或 chroot 中完成安装、验证、卸载和重装，并生成产物绑定证据。
- **目标机已验证**：真实 Kylin/UOS/openKylin 图形终端完成安装态 Electron、CLI、真实模型、附件、关窗退出和诊断导出验收。

四级证据不能互相替代。看到源码包或 DEB 文件不等于完整离线交付；Docker 通过不等于目标机已验证；旧 commit、旧包、旧日志和截图不能证明当前交付目录已经通过。最终 release 以当前 manifest、两类当轮证据、签名和 `scripts/taiji-release-check.sh` 为准，不以某个历史 commit 名称口头认定。

严格区分两个目录：`taijiagent 打包交付/` 是内部发布与验收工作区，不整体交付客户；`publish-single-deb.sh` 最终生成的全新目录才是客户交付目录。后者必须且只能有一个固定 basename 的 DEB。

## 构建前置：源码策略和统一支持矩阵

正式源码以 `packaging/linux/compatibility-policy.json` 作为唯一兼容策略和 Debian Maintainer 来源；构建脚本不再读取人工维护人文件、终端环境变量或目标机 profile。

第一版统一包固定支持：`x86_64/amd64`、图形桌面、`dpkg/apt`、Kylin/UOS/openKylin 家族，并由 `packaging/linux/certification-matrix.json` 固定六个正向类别和六个负向边界。代表性终端只用于形成认证记录，不参与生成 DEB；任何终端都不需要先采集基线再生成安装包。

认证记录必须绑定同一候选 DEB、同一 policy SHA 和同一源码 commit；认证结果 `CERTIFIED/BLOCKED` 不能由安装包自行伪称。

## 推荐拷贝路径

在本地仓库先执行：

```bash
bash "taijiagent 打包交付/99_本机_准备制包输入包.sh"
```

脚本会刷新当前 commit 对应的唯一源码包及其 `*.inventory.json` 成员清单，使 `SHA256SUMS.txt` 精确只绑定这两个文件，并生成：

```text
taijiagent-制包机输入-<hash>.tar.gz
taijiagent-制包机输入-<hash>.manifest.json
taijiagent-制包机输入-<hash>.tar.gz.sha256
```

输入包只接受源码受控的固定文件清单，不扫描或打入 macOS 拷贝元数据、旧构建目录、历史安装产物、日志或发布证据。把同一 commit 的三件套一起拷贝到联网 Linux amd64 制包机；传输前后分别记录 basename、字节数和 SHA256。制包机先在三件套所在目录执行：

```bash
sha256sum -c taijiagent-制包机输入-<hash>.tar.gz.sha256
```

校验通过后再解压 `tar.gz`，进入其中的 `taijiagent 打包交付` 目录继续执行第一步。正式制包不再接受直接复制本地工作目录作为等价输入；如果任一三件套文件缺失、commit 不一致或摘要不一致，必须重新从同一冻结提交生成，不能在制包机上临时补文件。

`00_制包机_生成离线交付包.sh` 在 Python 构建依赖可用后还会调用输入包内的固定验证器，重新核对三件套、manifest 的精确字段、包内固定成员和当前解压目录。命令行 sidecar 校验只是传输前置检查，不能替代这道正式门禁。

制包成功前，`生成的安装包/` 不存在可用候选产物；制包成功后，内部验收人员可把整个 `taijiagent 打包交付` 工作区拷贝到断网演练环境和真实目标机。客户安装时只使用最终发布的单一 DEB，不使用这个内部目录。

允许通过 FAT/exFAT U 盘、压缩包或其他不保留 Unix 可执行位的介质中转；发布清单按路径和内容摘要绑定，不把安全的 `0644/0755/0700` 差异误判为内容篡改。各脚本统一使用 `bash ./脚本名.sh` 执行，不依赖介质保留可执行位。软链接、硬链接以及 group/other 可写文件仍会被门禁拒绝；如果中转介质把文件呈现为 group/other 可写，请先用安全 umask（例如 `umask 022`）复制到目标 Linux 本地文件系统后再执行，不要关闭权限检查。

## 内部制包与验收目录

内部验收时，把整个文件夹拷贝到目标终端任意位置：

```text
taijiagent 打包交付
```

不要只拷贝里面的单个脚本。内部目标机验收的完整文件夹必须包含源码包、制包机脚本、单一 DEB 及其 manifest/sidecar、安装验证脚本、诊断脚本和验收工具。这一规则不适用于门禁通过后的客户单 DEB 目录。

完整交付目录至少应包含：

```text
taiji-agentv1.0-kylin-build-src-<hash>.tar.gz
taiji-agentv1.0-kylin-build-src-<hash>.inventory.json
source-archive-integrity.py
SHA256SUMS.txt
00_制包机_生成离线交付包.sh
01_制包机_发布预检.sh
02_目标终端_安装并验证.sh
03_目标终端_导出诊断报告.sh
04_目标终端_桌面App验收并导出证据.sh
验收工具/
生成的安装包/
```

只有脚本、说明和源码包不算完整的内部验收输入，不能用于制包或验收。

## 第一阶段支持边界

- 系统：Kylin/UOS/openKylin 家族中满足 canonical policy 的版本和图形桌面
- 架构：x86_64 / amd64
- 包管理器：apt、apt-get、dpkg、systemctl
- glibc：不低于 canonical policy 声明的最低版本；构建后的 ELF ABI 审计不得超过该下限
- 图形桌面：需要能正常启动 Electron 桌面应用

不支持条件：

- RPM-only 终端：需要单独生成 RPM 包，不能用本 DEB 脚本硬装。
- ARM/aarch64 终端：需要单独的 ARM 构建链和 Electron runtime。
- 无包管理器或强隔离终端：后续应走 `.run` fallback，不属于当前 DEB 验收范围。
- 缺少桌面环境或 canonical policy 要求的系统基础能力：单 DEB 的 `preinst` 会报告 `BLOCKED`，不能靠补发第二个依赖包绕过统一包边界。

## 第一步：在联网 Linux amd64 制包机生成离线交付包

在制包机中打开这个文件夹，右键选择“在终端中打开”，然后执行：

```bash
TAIJI_UV_LOCK_MODE=strict bash ./00_制包机_生成离线交付包.sh
```

执行前请确认制包盘建议至少有 `20 GiB` 可用空间。新版脚本会在真正解压源码和下载依赖前强制检查：选中的构建文件系统必须至少剩余 `12 GiB` 和 `100000` 个可用 inode；不满足时会立即给出明确错误，不再等到制包后半程才报磁盘空间不足。

这个脚本会自动完成：

- 执行 `01_制包机_发布预检.sh`：检查 git 干净、源码包与当前 commit 匹配、`SHA256SUMS.txt` 精确绑定当前源码包和成员清单、交付目录没有旧 zip/macOS 元数据。
- 如果发现 `.DS_Store`、`._*`、`__MACOSX`、`.AppleDouble` 或 `PaxHeaders*`，脚本会打印路径并自动清理；上次中断留下的已知安全制包产物会整体移入 `旧版备份/`，未知文件会失败并保持原状。
- 执行管理员能力预检；如果当前用户不能 `sudo`，会在安装构建依赖之前失败并导出失败诊断，不会半跑后才报错。
- 校验制包机架构和包管理器；制包机不要求预装 Python，脚本会先通过 apt 安装
  `python3`/`python3-dev`，再执行依赖 Python 的构建根探针和源码发布预检。
- 校验源码压缩包没有传输损坏，并在解压后、构建前、DEB 打包前及最终预检时用独立工具逐成员复核可写源码树；任何临时改动都会停止制包。
- 安装依赖后按 `XDG_CACHE_HOME/taiji-agent-build-<uid>`、`$HOME/.cache/taiji-agent-build-<uid>`、`/var/tmp/taiji-agent-build-<uid>` 顺序选择 owner-only 专用构建根；每个候选先运行 ELF 和动态库加载探针，脚本将 `TMPDIR/TMP/TEMP` 统一指向选中根。`/tmp` 不再作为默认构建根；显式 `TAIJI_BUILD_ROOT` 探针失败会立即停止，失败诊断会记录 `findmnt -T`，不要关闭麒麟安全策略。
- 重建受控构建根后检查可用 block 和 inode；最终源码比对、DEB 真实解包和只读 payload 清理都使用同一受控临时根，不会悄悄绕回 `/tmp`；终端中断或关闭时也会只在该受控范围内回收本轮临时文件。
- 安装构建依赖，并在下载 Python/Node 依赖前一次性校验 `readelf`、`strings`、`perl`、`cmp`、`ldd`、`getconf` 等后续命令闭包。
- 始终在 owner-only 构建根准备并校验固定 `uv 0.12.2` 归档和可执行文件；不使用 PATH 中的系统 uv，也不调用在线 installer。
- 始终在 owner-only 构建根准备并校验固定 Linux x64 Node.js `22.23.1`，不因系统 Node/npm 版本看似相同而复用它。
- 始终从固定 standalone 归档准备 Python `3.11.15`，用该可执行文件创建 production venv，不携带 `debugpy`/`pytest` 等开发调试工具。系统 `python3` 只负责启动受审 helper，不是打入 DEB 的 Python 来源。
- 通过 npm 获取 Linux Electron runtime；下载 ZIP 只能位于本轮受控构建缓存，basename、版本和 SHA256 必须与 canonical policy 一致。实际打入 DEB 的 `electron` ELF 只能从该 ZIP 安全解出，完整 `dist/` 文件清单、逐文件内容和可执行文件 SHA256 都必须精确匹配；替换 `node_modules` 内运行时不能通过。
- 校验默认非密产品配置已进入源码包，且不包含任何敏感凭据。
- 校验 WebUI 运行时资产已本地化，不依赖 jsdelivr/CDN。
- 校验附件上下文能力进入源码包，支持 PDF、PPTX、DOCX、XLSX、TXT/MD/CSV 和图片上传后的对话消费。
- 构建 `amd64 .deb` 安装包。
- 校验蓝色太极 Logo 的 RGBA PNG、hicolor 多尺寸、ICO、AppStream、desktop-id/WM_CLASS、Electron 主/登录窗口图标和安装态资源同源。
- 以 closed-world 口径审计最终 DEB payload，确认每个 ELF 依赖只能由包内私有库、Electron 固定 companion、审计器固定的基础运行时边界或 policy 明确列出的少量系统 SONAME 解决；制包机已经安装的共享库不能替最终 DEB 充数。Python venv、Electron Linux ELF、Web runtime、脚本和桌面入口都必须在包内，并剔除 Tcl/Tk、调试器和非 x86_64-glibc 的 resvg 原生包。
- 把生成的安装包复制到本文件夹下的 `生成的安装包/`。`.build-success` 先在 owner-only 构建根作为待发布标记；只有源码树复核、manifest/报告、验收工具、权限归一化和最终 `01` 全部通过后，才会以不覆盖方式原子发布到输出目录；中途失败不得留下公开成功标记。
- 生成 `taiji-package-manifest.json`、构建报告和 SHA256 校验信息。
- 收集 `04_目标终端_桌面App验收并导出证据.sh` 及 `验收工具/`，并把它们纳入确定性发布清单。
- 制包主日志、`setup-local` 日志和失败诊断只保存在制包机 `~/.local/state/taiji-agent/build-logs/`（设置 `XDG_STATE_HOME` 时使用其对应目录），不写入完整交付目录，避免把制包机路径和内部日志交付客户。

新版构建会检查 Agent 的产品运行时入口。交付文件夹放在带空格或中文的路径下，也不会因为控制台脚本 shebang 路径解析失败导致双击后 Agent 启动失败。

如果日志里出现下面这种内容，说明源码中提交的 `uv.lock` 与当前依赖声明不一致。正式构建会按设计中断，不会生成可发布安装包：

```text
The lockfile at `uv.lock` needs to be updated, but `--locked` was provided.
```

处理方式：不要在制包机现场刷新 lock，也不要改成 `auto` 或 `unlocked` 继续制包。回到源码仓库修正依赖与 `uv.lock`，完成测试和提交后，重新生成制包输入包。正式入口只接受未设置或 `TAIJI_UV_LOCK_MODE=strict`；只要设置 `TAIJI_ALLOW_UV_LOCK_REFRESH` 就会被拒绝。脚本使用专用变量 `TAIJI_UV_INDEX_URL`，不会被制包机已有的通用 `UV_INDEX_URL` 环境变量意外改写；只有经过验证、并与 lock 一致的内网镜像才能覆盖该变量。

正式制包工具也是固定的：Python `3.11.15` 的 standalone 归档 SHA256 必须为 `2ed5c2b6d2a018e0345219d6391a85b1eb0d0d1752b19cde6fc210d9392a752a`，其 `python3.11` 可执行文件 SHA256 必须为 `5035e46784be79111e00103f91b37bcd3b26f2b8b936f26e2bd4bb8252cd0aba`；`uv 0.12.2` 必须同时通过官方归档 SHA256 `d66e96b5f1ca3b99806eee283a8125d33a0bd669e6e6d9bc4ab7ffda63c41bf4` 和可执行文件 SHA256 `72c5f455cd0e9793910f6a1db255de37b610a36a8db858afa3c72e34668e23e2` 校验；Node.js `22.23.1` 必须同时通过官方归档 SHA256 `9749e988f437343b7fa832c69ded82a312e41a03116d766797ac14f6f9eee578` 和可执行文件 SHA256 `93956de2e59480474a7b46571da1651180b1a050cdf32641ebec4ce6e478e068` 校验；Electron `39.8.10` 的实际 `electron` ELF SHA256 必须为 `c63780578ca420c8651b81544e1551cef8b71a31c64712378467ed30dae06f6d`。不使用系统 PATH 中同名工具代替。

如果日志里出现下面这种内容，说明 WebUI 静态资源还残留运行时 CDN 依赖，完全离线包会被发布门禁拒绝：

```text
WebUI static assets still depend on CDN
```

处理方式：换用当前新版输入包。新版源码已把 PDF.js、Mermaid、xterm、Prism、KaTeX、js-yaml 等运行时静态资产放到 `static/vendor/`，并在本地发布预检中扫描 `cdn.jsdelivr.net`、`unpkg.com`、`cdnjs.cloudflare.com`。

如果制包机能访问 apt 源，但某个 Node/npm/Electron 镜像 DNS 解析失败，脚本会自动切换内置备用源；如果现场网络只能访问指定内网镜像，可在执行前显式指定：

```bash
export TAIJI_NODE_MIRRORS="https://你的内网镜像/node https://nodejs.org/dist"
export TAIJI_NPM_REGISTRIES="https://你的内网npm源 https://registry.npmjs.org"
export TAIJI_NPM_AUDIT_REGISTRY="https://registry.npmjs.org"
export TAIJI_ELECTRON_MIRRORS="https://你的内网electron镜像/ https://github.com/electron/electron/releases/download/"
bash ./00_制包机_生成离线交付包.sh
```

`TAIJI_NPM_REGISTRIES` 只负责依赖下载，可以使用 `npmmirror` 等国内镜像；`npm audit` 需要支持 npm 安全审计 API 的 registry，因此默认单独使用 `https://registry.npmjs.org`。如果现场只能访问内网，请把 `TAIJI_NPM_AUDIT_REGISTRY` 设置为实现该审计接口的 HTTPS 内网源。该 URL 不得内嵌账号、密码或 token；需要认证时应使用现场受控的标准 npm 配置。审计接口不可用、返回异常或发现 high/critical 漏洞时，正式制包都会继续中断，不能通过关闭审计绕过。

制包成功后，你会看到：

```text
生成的安装包/taiji-agent_1.0.0_amd64.deb
生成的安装包/taiji-agent_1.0.0_amd64.deb.sha256
生成的安装包/taiji-package-manifest.json
生成的安装包/构建报告.txt

```

### 在受控发布机生成离线演练证据

把制包成功后的完整 `taijiagent 打包交付/` 放回受控发布机的当前仓库，然后在仓库根目录执行：

```bash
docker build --platform linux/amd64 \
  -t taiji-offline-rehearsal:local \
  tools/taiji-offline-rehearsal

export TAIJI_OFFLINE_REHEARSAL_CHALLENGE="$(openssl rand -hex 32)"
# 标准 Task9 全生命周期入口：N-1 DEB 必须来自受控归档，并带同名 .sha256 sidecar。
python3 scripts/produce-taiji-offline-rehearsal.py \
  --deb "taijiagent 打包交付/生成的安装包/taiji-agent_<version>_amd64.deb" \
  --previous-deb "/受控归档/N-1/taiji-agent_<n-1-version>_amd64.deb" \
  --build-manifest "taijiagent 打包交付/生成的安装包/taiji-package-manifest.json" \
  --policy "packaging/linux/compatibility-policy.json" \
  --output-dir "taijiagent 打包交付/offline-install-rehearsal" \
  --image taiji-offline-rehearsal:local \
  --challenge "$TAIJI_OFFLINE_REHEARSAL_CHALLENGE"

# 当前 v3 单 DEB 目录入口（用于 fresh/reinstall，不包含 N-1 全生命周期）：
python3 scripts/produce-taiji-offline-rehearsal.py \
  --delivery-dir "taijiagent 打包交付" \
  --output-dir "taijiagent 打包交付/offline-install-rehearsal" \
  --image taiji-offline-rehearsal:local \
  --challenge "$TAIJI_OFFLINE_REHEARSAL_CHALLENGE"
```

`--output-dir` 指向的输出目录必须不存在；如果已有历史目录，先将整个目录归档，不要覆盖或混写旧证据。显式全生命周期入口中，N-1 的 Debian 版本（含 epoch、upstream version 和 revision 语义）必须严格小于当前候选；同版本或更高版本不得冒充 N-1。生产器会只读挂载交付目录，并在容器运行时强制使用 `--network none`，只使用本地交付物完成安装、卸载和重装。成功时输出 `schema=taiji.offline-install-rehearsal.v1`、`status=PASS` 的当前证据，它绑定 v3 manifest 中的 source commit/version、唯一 DEB、canonical policy、previous DEB basename/version/SHA256，以及同目录的基础会话和扩展生命周期原始日志，不包含历史 target baseline 字段。认证集会整目录归档并复核该证据 JSON、两份日志及其逐文件清单，缺失、替换或把同版/新版冒充 previous 都不能签名或发布。历史 v2 只能显式使用 validator 的 `--legacy-v2-read-only` 查看，不能作为当前发布证据。保留本次 `TAIJI_OFFLINE_REHEARSAL_CHALLENGE` 的原值，后续签名和最终放行必须复用同一个值，不得重新生成。

注意：当前这项门禁只能证明 `previous < candidate`，尚不能独立证明 previous 就是发布台账中“紧邻的上一个已签名版本”。在 prior release-evidence/signature 绑定或首发 signed waiver 门禁完成前，不得把这项测试表述为“已证明紧邻 N-1”。

标准显式入口会在内部演练容器中生成受控的 N-1 签名占位文件，仅验证事务材料的文件绑定；它不替代发布模式的 detached signature 密码学验签。客户/销售放行仍必须使用已归档的 N-1 签名材料并通过 release admission。

该证据仅证明离线安装生命周期，不能替代真实 Electron 桌面 App 验收。桌面放行仍必须在实际 Kylin/UOS/openKylin 目标终端执行第四步。

演练镜像固定使用与当前制包依赖链一致的 Ubuntu 20.04 x86_64 兼容基线，避免把 Debian 新版本的系统包冲突误判为交付包缺陷。镜像不会预装一整套宽泛桌面依赖，只安装 canonical policy 明确要求目标系统提供的 SONAME 对应包；其余共享库必须由 DEB 自身携带并通过 closed-world 审计。它仍只是目标终端验收前的容器回归，不能替代麒麟、统信或 openKylin 真机验收。

## 第二步：内部验收目录拷贝到完全离线目标机

由内部验收人员把整个 `taijiagent 打包交付` 文件夹拷贝到目标机。目标机不需要联网，不执行 `npm ci`、`uv sync`、`curl` 或在线 `apt update`。这一步用于生成发布证据，不是最终客户安装方式。

## 第三步 A：内部单 DEB 安装生命周期验证

在目标机同一个文件夹中执行：

```bash
bash ./02_目标终端_安装并验证.sh
```

`02` 默认使用 `certification` admission，仅用于受控的内部离线演练；客户/销售放行必须由发布负责人显式设置 `TAIJI_ADMISSION_MODE=release`，并同时提供已签名的 `TAIJI_RELEASE_EVIDENCE`、`TAIJI_RELEASE_SIGNATURE` 和对应 `TAIJI_RELEASE_PUBLIC_KEY`。没有这些签名材料时不得把 certification 结果当作销售发布证明。

这个脚本会自动完成：

- 检查第一步写入的 `.build-success` 成功标记；没有成功标记不会安装旧包。
- 校验 `taiji-package-manifest.json` 与 `.build-success`、唯一 DEB 及其 sidecar 匹配。
- 校验 `.deb` 文件。
- 在解包前由 DEB `preinst` 检查 canonical policy 要求目标系统提供的共享库；缺少任一项会明确返回 `TAIJI-LINUX-E014-RUNTIME`，不会先写入半包。
- 在任何新包安装前，先把已校验的单一 DEB、同名 `.sha256`、manifest、policy 和管理脚本复制到 root-owned `/var/tmp/taiji-agent-management.*` staging，再由静默部署器把 DEB 固化到 `/var/tmp/taiji-agent-deploy.*` 并再次核对摘要。management staging 中的 DEB 与 sidecar 必须成对保留原始 DEB 文件名；不能改名为 `candidate.deb` 或 `previous.deb`，否则 sidecar 文件名绑定会在安装前失败。
- 安装动作不修改 apt source，不执行 `apt update`，不下载任何第二个包，也没有在线 fallback。
- 受 `dpkg` 管理的现有 `taiji-agent` 直接走原生升级/同版本重装；不会先解除 hold、purge、强制删除包状态或手工删除 `/opt/taiji-agent`。
- 仅当系统没有 `dpkg` 包状态、但存在明确白名单内的旧浏览器 WebUI 残留时，才进入 legacy 迁移；迁移只清理固定的旧安装、服务和系统入口，不扫描或删除用户 XDG 数据。
- 停止旧进程时按 `/proc/<pid>/exe` 的物理可执行文件是否位于 `/opt/taiji-agent/` 下判定，并在强制停止前再次核验 PID 身份；不再按命令行模式或端口盲杀。
- 检查 `8787`、`18642`、`18787` 端口，遇到非太极 Agent 进程占用会记录诊断但继续安装；新版桌面端会自动选择空闲本地端口，不会误杀其他软件。
- 管理端把脚本、控制文件、manifest、候选 DEB 和升级输入复制到 root-owned `/var/tmp/taiji-agent-management.*`，再由静默部署器把候选 DEB 固化到 root-owned `/var/tmp/taiji-agent-deploy.*`；安装动作不执行 `apt update`、在线下载或在线回退。
- 如果机器上已经装过 `taiji-agent`，脚本会用当前生成的安装包原地同版本重装或按显式 upgrade/rollback 合同处理；普通客户 fresh install 不携带 N-1 升级材料。
- 运行安装态诊断命令，并提前验证 Agent CLI 模块入口。
- 验证默认非密配置已同步到当前用户运行态，模型配置和菜单显隐接口可用。
- 在图形桌面会话中尝试 Electron smoke test。
- 检查 `taiji` 命令入口。
- `02` 在目标机执行失败时，会把当次安装诊断写入目标机当前交付目录的 `构建日志/失败诊断-<时间>.txt`，里面包含目标机环境、包状态、服务状态、端口占用、最近日志和下一步建议。
- 如果 `dpkg --install` 返回非零，静默部署器会直接回显 root-only 安装日志的最后 80 行，保留维护者脚本和 native verify 的真实错误，不再只显示笼统的“安装失败”。
- `dpkg` 安装成功后的二次验证以 `--system-only` 模式运行，不依赖 root 环境中是否有 `HOME`，也不会把已经通过 `postinst` 的安装因“无用户 HOME”再误判为失败。如果 verifier 缺失或执行失败，部署必须失败关闭；安装、回滚和二次校验的 root-only `0600` 日志会在失败时回显最后 80 行，成功回执只能是 `native_verify=PASS`。
- 安装态校验会固定 `PYTHONDONTWRITEBYTECODE=1`，不会以 root 在 `/opt/taiji-agent` 中生成未登记的 Python 缓存。正式断网演练会核对安装清单外文件，并要求 `dpkg --purge` 后 `/opt/taiji-agent` 完全不存在；这两项任一失败都必须废弃当前候选并重新制包，不能让现场手工删除残留来伪造通过。
- 极简系统 purge 后如果空 `/opt` 被 dpkg 一并移除，重装预检会在受信根文件系统上继续执行相同的 6144 MiB、noexec 和写入 canary 门禁，并让 dpkg 正常重建 `/opt`；不会把“目录尚不存在”误报成磁盘不足。`/opt` 若是软链接、断链或普通文件仍会失败关闭。root management 暂存同时禁止 Python 写入 bytecode，成功或失败后都不应留下本轮 `/var/tmp/taiji-agent-management.*` 空壳。

如果失败回执显示 `DEB_SHA256_SIDECAR_MISMATCH`（upgrade 的 N-1 输入还可能显示 `PREVIOUS_DEB_SHA256_SIDECAR_MISMATCH`），不要手工改 DEB 文件名或修改 `.sha256`。这表示使用的 `02` 在 root staging 中破坏了 DEB basename 与 sidecar 的绑定；请重新拷贝由当前正式源码生成的完整交付目录后重试。这个修复只闭合内部安装脚本的暂存合同；只有重建后的同一 DEB 完成断网生命周期和真实 Kylin/UOS/openKylin 图形终端验收，才能分别记为“离线安装已演练”和“目标机已验证”。

如果显示 `TAIJI-LINUX-E014-RUNTIME`，表示这台机器缺少统一 policy 规定必须由操作系统提供的基础共享库。不要在离线终端手工复制来历不明的 `.so`，也不要为某一台机器临时改包；请导出 `03` 诊断，确认该系统是否仍在第一阶段支持矩阵内。若最后 80 行出现 `/opt/taiji-agent/` 下 Electron 或 native verify 的 `not found`，这是候选 DEB 的运行时闭包缺口，不是让现场逐台补库的问题；立即停止使用该候选，回到正式源码重建并完成断网生命周期演练。

该路径用于内部生命周期和故障诊断，不是客户“只双击一个文件”的证据。执行过本步骤后，当前系统已经安装了 `taiji-agent`，不能再直接声明单 DEB 路径的安装前状态为 `not-installed`。

## 第三步 B：干净目标机单 DEB 双击安装

销售放行必须另用符合统一兼容策略的干净图形终端，不能先在这台机器执行 `02`。把 manifest 指定 basename 的当前候选 DEB 单独复制到一个新目录；目录中必须只有这一个实体普通文件。断开或禁用全部非 loopback 网络，并确保当前用户没有既有太极配置、数据、状态、缓存或 Electron user-data。

由发布负责人生成当轮 challenge；终端 A 创建一个全新的实体证据目录，然后在安装前启动系统 Python 观察器。观察器会一直占用终端，直到 dpkg 从无记录变为安装完成：

```bash
export TAIJI_TARGET_ACCEPTANCE_CHALLENGE="$(openssl rand -hex 32)"
export TAIJI_SINGLE_DEB_CUSTOMER_DIR="/只有当前manifest同名候选DEB的绝对目录"
export TAIJI_INSTALL_EVIDENCE_DIR="$PWD/install-observation-$TAIJI_TARGET_ACCEPTANCE_CHALLENGE"
mkdir -m 0700 "$TAIJI_INSTALL_EVIDENCE_DIR"

/usr/bin/python3 -B ./验收工具/observe-single-deb-install.py observe \
  --customer-dir "$TAIJI_SINGLE_DEB_CUSTOMER_DIR" \
  --manifest "$PWD/生成的安装包/taiji-package-manifest.json" \
  --challenge "$TAIJI_TARGET_ACCEPTANCE_CHALLENGE" \
  --output-dir "$TAIJI_INSTALL_EVIDENCE_DIR"
```

观察器运行期间，在终端 B 通过文件管理器双击唯一 DEB，并使用系统图形包安装器完成安装。不要停止观察器、不要恢复网络、不要替换候选目录或 DEB。若观察器报错、图形安装器要求下载依赖、需要第二个安装文件或网络必须恢复，本次单 DEB 离线验收失败，应回到兼容策略和依赖设计修复。

安装完成后保存一张完整的系统图形安装器成功界面 PNG，至少 800x600。操作员再出具范围严格的人工见证：

```bash
/usr/bin/python3 -B ./验收工具/observe-single-deb-install.py attest \
  --observation "$TAIJI_INSTALL_EVIDENCE_DIR/single-deb-install-observation.json" \
  --graphical-evidence "/绝对路径/系统图形安装器成功界面.png" \
  --challenge "$TAIJI_TARGET_ACCEPTANCE_CHALLENGE" \
  --operator-id "<受控操作员编号>" \
  --confirmation "I-observed-desktop-double-click-and-system-installer" \
  --output-dir "$TAIJI_INSTALL_EVIDENCE_DIR"
```

机器观察记录证明安装前无 dpkg 记录、候选目录/DEB 未变化、安装期间持续未发现非 loopback 网络、同机同启动周期和 dpkg 状态迁移；它不能识别鼠标双击。`desktop-double-click` 是现场人员人工见证，必须由发布负责人结合有效系统安装器 PNG 复核，并在最终对顶层证据签名时承担真实性责任。

注意：原生 `dpkg` 升级不会在安装前删除旧安装，维护者 `postinst` 失败也不会自行恢复旧二进制。显式 `management upgrade` 在提供 N-1 DEB、`.sha256`、detached signature、N-1 manifest/数据契约和业务用户后才会先快照用户数据并尝试恢复。`management rollback` 是单向降级：`TAIJI_PREVIOUS_DEB` 是降级目标，不绑定当前版本 DEB 作为第二个恢复制品；降级过程的 dpkg/native verify 失败必须输出 `manual_recovery_required`，不能声称自动回到降级前版本。升级恢复失败也会保留 `manual_recovery_required`，不能把普通 `dpkg --install` 说成自动回滚。

从历史 DEB 首次直接升级时，`dpkg` 会先执行当前已安装旧包里的 `prerm`；新包无法追溯修改这个“首跳”脚本。该场景必须在真实目标机升级验收中单独覆盖；如果旧 `prerm` 失败，停止反复安装，先导出诊断交由交付支持处理。

不要在存在任何 `dpkg` 包状态时手工删除 `/opt/taiji-agent`。手工删除只能在交付支持明确确认“无 `dpkg` 状态且属于固定白名单 legacy 残留”后执行；正常情况交由 `02_目标终端_安装并验证.sh` 自动判定和迁移。用户 XDG 配置、模型 Key 和历史会话不在该清理范围。

### 无图形会话的离线安装演练

正常执行时必须存在 `DISPLAY` 或 `WAYLAND_DISPLAY`。无图形会话时，脚本默认失败，不会输出普通的“安装验证命令已执行完毕”。

只在干净 VM、chroot 或容器中做不带桌面验收的离线安装演练时，才可显式执行：

```bash
TAIJI_ALLOW_HEADLESS_REHEARSAL=1 bash ./02_目标终端_安装并验证.sh
```

该分支只继续安装态非 GUI 诊断和 CLI 入口检查，并会明确输出“仅离线安装演练，不是桌面 App/目标机验证”。Electron 桌面 App、真实模型对话和目标机验证仍是“未验证”，不得用该结果替代实际 Kylin/UOS/openKylin 目标机验收。

## 第四步：用真实 Electron 桌面 App 验收并导出证据

单 DEB 安装观察与人工见证完成后，不要先手工启动 App。按现场策略恢复可访问的本地或内网模型，并用受控方式向验收进程提供已批准的真实 Provider 凭据；不得把凭据写入脚本、命令历史、安装包或证据目录。在同一机器、同一启动周期和同一 challenge 下执行：

```bash
export TAIJI_SINGLE_DEB_INSTALL_OBSERVATION="$TAIJI_INSTALL_EVIDENCE_DIR/single-deb-install-observation.json"
export TAIJI_SINGLE_DEB_METHOD_ATTESTATION="$TAIJI_INSTALL_EVIDENCE_DIR/single-deb-install-method-attestation.json"
export TAIJI_SINGLE_DEB_GRAPHICAL_INSTALLER_EVIDENCE="$TAIJI_INSTALL_EVIDENCE_DIR/single-deb-graphical-installer.png"
bash ./04_目标终端_桌面App验收并导出证据.sh
```

`04` 不再接受 `TAIJI_TARGET_INSTALL_METHOD`、`TAIJI_TARGET_INSTALL_NETWORK`、`TAIJI_TARGET_DPKG_STATUS_BEFORE` 或 `TAIJI_TARGET_FIRST_LAUNCH` 这类事后自报布尔值。它先验证机器观察记录、人工见证、PNG、challenge、机器/启动周期、候选和时间顺序，再且只会验收安装态 Electron App：

1. 核对已安装包、Electron 可执行文件、desktop entry 与当前 manifest 的摘要。
2. 真实启动 `/opt/taiji-agent` 安装态 Electron，不使用 Web 页面或手机端替代。
3. 在可见对话界面上传带本次 challenge 的文本附件，要求真实模型只返回附件中的唯一验收码，并同时核对 UI 与持久化会话。
4. 截取真实 App 画面，通过设置里的可见入口导出脱敏支持包。
5. 关闭窗口，确认 Electron、Agent、界面服务进程与端口都退出。
6. 驱动必须从可见首次配置工作台开始，通过真实可点击控件推进，并在服务端确认 `completed=true` 且 preflight 全部就绪后才继续；与观察器的首启前空状态证据组合支持“首次配置周期已完成”。
7. 生成 `target-verification/` 中的会话 JSON、App PNG、图形安装器 PNG、机器观察、人工见证、诊断 JSON、driver result 和顶层 JSON，并先执行未签名完整校验。

如果任一项失败，不会保留可被误认为通过的正式证据。成功后把整个 `target-verification/` 复制回受控发布主机，由发布负责人核对截图和诊断内容后使用离线私钥签名。私钥不得复制到目标终端。

上述是受控现场的软件采样、人工见证和发布批准证据，不是 TPM/远程证明。掌握目标机 root 的恶意管理员不在该证据链的可对抗范围内；签名证明的是审批和收到后的完整性，不是原始事实对恶意 root 不可伪造。

## 最终销售发布：只生成一个客户 DEB

断网演练证据和真机证据都复核、签名，正式 `main` 全部门禁通过后，在受控发布机执行：

```bash
export TAIJI_CERTIFICATION_CHALLENGE="<当轮认证集原值>"
export TAIJI_PUBLICATION_CHALLENGE="<当轮发布回执原值>"
mkdir -p customer-output internal-release-receipts
bash packaging/linux/deb/publish-single-deb.sh \
  --delivery-dir "$PWD/taijiagent 打包交付" \
  --candidate-deb "$PWD/taijiagent 打包交付/生成的安装包/taiji-agent_<version>_amd64.deb" \
  --policy "$PWD/packaging/linux/compatibility-policy.json" \
  --certification-set "$PWD/taijiagent 打包交付/certification/certification-set.json" \
  --certification-signature "$PWD/taijiagent 打包交付/certification/certification-set.json.sig" \
  --release-evidence "$PWD/taijiagent 打包交付/release-evidence.json" \
  --release-signature "$PWD/taijiagent 打包交付/release-evidence.json.sig" \
  --output-dir "$PWD/customer-output/taiji-agent-linux-amd64" \
  --receipt-root "$PWD/internal-release-receipts/single-deb"
```

`--output-dir` 必须事先不存在。publisher 输入固定为候选 DEB、canonical policy、signed certification set 和 signed v3 release evidence；客户文件名严格为 `taiji-agent_${VERSION}_amd64.deb`，不会加入 profile。最终客户 DEB 与已认证候选 SHA256 必须完全相同。正式 release-check 期间，publisher 还会快照认证集中全部 `records/` 附件和 `offline-rehearsal/` 原始证据，任何增删、替换或内容改动都会失败且不产生客户目录。publisher 的六文件 receipt 只是单 DEB 发布回执，不是完整认证档案；完整 `certification/records/`、`certification/offline-rehearsal/` 及其它受控原始附件必须在内部认证归档中持续保留。客户只拿该新目录中唯一的 `.deb`；完整工作区、签名私钥和内部验收材料不交付客户。

## 第五步：人工双击启动复核

在图形桌面会话中安装验证脚本通过后，从开始菜单搜索并打开：

```text
太极 Agent
```

验收顺序：

1. 双击“太极 Agent”能打开窗口。
2. 首屏进入对话界面。
3. 再双击一次只聚焦已有窗口，不新开抢端口。
4. 关闭窗口后，本次本地会话停止。
5. 再次双击能重新打开。
6. 确认首次配置周期已经通过可见工作台完成；使用已配置模型发送一句测试消息，确认真实对话返回。
7. 上传一份 PDF/PPTX/DOCX/XLSX 或 TXT/MD/CSV 文件后提问“这个文件说了什么”，回复应基于文件内容，而不是泛泛介绍太极 Agent。
8. 上传一张图片后提问“图里有什么”；如果当前主模型或辅助视觉模型支持图片，应基于图片内容回答；如果未配置视觉能力，应明确提示当前无法分析图片。

Linux 桌面版会隐藏应用菜单栏，不再显示顶部“太极 Agent / 视图”菜单；仍保留麒麟系统原生的最小化、最大化和关闭按钮。

## 第六步：导出诊断报告

如果页面样式、菜单、模型下拉、对话或启动过程仍有异常，在同一个交付文件夹里执行：

```bash
bash ./03_目标终端_导出诊断报告.sh
```

脚本会生成：

```text
诊断报告/taiji-agent-diagnose-<时间>.txt
```

诊断报告会收集包状态、端口、进程、桌面入口、用户态配置摘要、WebUI API 状态、附件解析器状态、图片视觉路由状态和最近日志尾部，并自动脱敏常见密钥字段。后续排查时优先发送这个 txt 文件。

## 重要边界

- 安装包不内置模型 API Key、微信 token、企业微信 Secret、服务器地址或私钥。
- 安装包会内置非密默认产品配置，用来保证菜单显隐、默认模型展示和首页控件与本地产品配置一致；密钥仍需首次进入界面后本机配置。
- 上传附件时，聊天界面只显示文件名，不显示目标机或本机的绝对路径；密钥文件、私钥和疑似密钥文件不会被注入模型上下文。
- 新版安装后只保留开始菜单“太极 Agent”桌面入口；旧浏览器访问版不会作为并存产品保留。
- 仅当系统没有 `dpkg` 包状态且脚本确认为固定白名单内的 legacy WebUI 残留时，安装脚本才会迁移旧系统安装和 `/opt/taiji-agent`；普通用户家目录下的 `~/.config/taiji-agent`、`~/.local/share/taiji-agent`、`~/.local/state/taiji-agent` 不在清理范围。
- 未配置模型前，只能验证桌面壳、本地 Agent/WebUI 和安装链路，不能算真实模型对话已完成。
- 完全离线目标机只安装和验证，不构建、不访问外网。制包机使用与统一兼容策略及认证矩阵一致的 apt 源生成内部演练依赖；不按每台终端重新生成 DEB。

## 日志位置

制包机构建日志默认位于用户态目录，不进入客户交付包：

```text
~/.local/state/taiji-agent/build-logs/
```

如果设置了绝对路径 `XDG_STATE_HOME`，实际位置是 `$XDG_STATE_HOME/taiji-agent/build-logs/`。交付目录内如果残留旧 `构建日志/`，新制包脚本会拒绝继续；请先归档并移出，不要将其交付客户。目标机执行 `02` 产生的安装失败诊断仍在目标机当前交付目录下，只用于现场排障。

安装后的运行诊断日志在目标机：

```text
~/.local/state/taiji-agent/logs/
```

如果双击后弹出“太极 Agent 启动失败”，新版错误弹窗会显示最近脚本输出；同时保留上面运行诊断日志目录，重点查看桌面端和 Agent 的最近运行日志。

也可以直接执行：

```bash
bash ./03_目标终端_导出诊断报告.sh
```
